# 一、問題描述

## 1.1 題目背景

本題由 LineGO 提出，核心目標為：在用戶輸入上車地址後，系統能即時推薦最有可能的下車地址排序清單，協助用戶快速完成叫車行為。題目要求推薦結果需考量不同時段、平日/假日差異，以及用戶個人屬性，以在不同叫車情境下提供最貼近用戶需求的建議。

傳統叫車流程中，用戶每次都需手動輸入目的地，耗時且容易重複輸入相同地點。若系統能根據歷史行為與當前情境主動預測目的地，可大幅降低叫車摩擦，提升使用體驗。

## 1.3 目標輸出

給定用戶 ID、當前上車位置、時段、假日狀態及星期，系統輸出該用戶最有可能的 Top-K 下車地址排序清單。評估重點在於：正確答案是否排在前幾名、排名是否越前越好。


# 二、模型架構

## 2.1 整體設計思路

本系統採用兩階段推薦架構（Two-Stage Retrieval + Ranking），這是業界主流的推薦系統設計模式：

- Stage 1｜候選集生成（Candidate Generation）：從 address_v2_suggestion 表中撈出該用戶曾去過的所有下車地址，作為本次推薦的候選集。範圍窄、精準，避免從全量地址中盲目搜尋。
- Stage 2｜排序（Ranking）：對候選集中每個地址計算特徵，交由 LightGBM LambdaRank 模型打分排序，輸出 Top-K 推薦結果。

設計上刻意不做複雜的神經網路，原因是本題的最強信號（用戶歷史下車頻率）是高度稀疏的 count-based 特徵，樹模型在此類特徵上通常比深度學習更有效率，且訓練速度快、可解釋性高。

## 2.2 特徵工程

共設計 12 個特徵，分為原始頻率（6 個）與 log1p 轉換版（6 個）兩組。log1p 轉換用於壓縮頻率的長尾分佈，讓模型同時能捕捉絕對值與相對大小兩種訊號：



| 特徵名稱 | 類型 | 意義 |
| --- | --- | --- |
| user_end_freq | 個人化 | 用戶歷史去過該下車地址幾次（最強信號） |
| global_end_freq | 全局熱門度 | 全體用戶去過該下車地址的總次數（冷啟動 fallback） |
| hour_end_freq | 時段情境 | 相同時段（如早尖峰）去該地址的歷史頻率 |
| holiday_end_freq | 假日情境 | 相同假日/平日狀態下去該地址的歷史頻率 |
| dow_end_freq | 星期情境 | 相同星期幾去該地址的歷史頻率 |
| start_end_freq | 上車情境 | 從相同上車區域出發前往該地址的歷史頻率 |
| log_* (×6) | 對數轉換 | 上述六個特徵各自取 log1p，捕捉相對大小訊號 |

## 2.3 訓練資料建立

對每一筆行程記錄，以「用戶 × 叫車情境」為一個 query，建立以下樣本：

- 正樣本（label = 1）：該筆行程的真實下車地址。
- 負樣本（label = 0）：從同用戶候選集中隨機抽取 4 個非真實答案的地址（NEG_RATIO = 4）。

每個 query 的候選集來自 suggestion 表，代表用戶曾使用過的地址，確保負樣本是「有意義的干擾項」而非隨機雜訊。同時對負樣本做 downsampling 控制正負比例，避免過度不平衡。

## 2.4 模型：LightGBM LambdaRank

本系統採用 LightGBM 的 LambdaRank 目標函數，這是一種 Listwise Learning to Rank 方法：

- 與普通二分類不同，LambdaRank 以整個候選列表為單位進行優化，直接最大化 NDCG 排序指標。
- 每個用戶的候選地址集合對應一個 group，模型學習「在同一個 query 裡，哪個候選地址應該排在前面」。
- 主要超參數：學習率 0.05、葉節點數 63、迭代 300 輪，特徵與樣本各 80% 抽樣，使用 GPU（NVIDIA T4）加速訓練。
## 2.5 訓練流程

完整訓練分為五個步驟：

- Step 1｜讀取資料：載入兩張 parquet 表，過濾行程數 ≥ 20 筆的有效用戶。
- Step 2｜預計算頻率查找表：將六類特徵預聚合為 dict，後續逐樣本 O(1) 查詢，避免大型 merge 佔用過多記憶體。
- Step 3｜建立訓練樣本：逐用戶配對正負樣本，90% 用戶作為訓練集、10% 作為 held-out 測試集。
- Step 4｜LightGBM LambdaRank 訓練：300 輪迭代，訓練完成後儲存 checkpoint 至 Google Drive。
- Step 5｜評估：在測試集計算 Recall@K、MRR@K、NDCG@K（K = 1, 3, 5）。

## 3.5 Step 5｜模型評估

### 3.5.1 評估指標說明

評估在 held-out 測試集（84,570 筆，562 位用戶）上進行，推論與指標計算共耗時約 1 秒（1.95 step/s）。



| 指標 | 定義 |
| --- | --- |
| Recall@K | 正確答案是否出現在前 K 名推薦中（Hit = 1，否則 = 0），反映覆蓋率 |
| MRR@K | Mean Reciprocal Rank，正確答案排名倒數的平均值（第 1 名 = 1.0，第 2 名 = 0.5），反映排名品質 |
| NDCG@K | Normalized Discounted Cumulative Gain，對排名位置加權後正規化的綜合品質分數，1.0 為最佳 |

### 3.5.2 評估結果


| K | Recall@K | MRR@K | NDCG@K |
| --- | --- | --- | --- |
| 1 | 0.9804 | 0.9804 | 0.9804 |
| 3 | 1.0000 | 0.9896 | 0.9782 |
| 5 | 1.0000 | 0.9896 | 0.9767 |


### 3.5.3 各指標逐項解讀

Recall@1 = 0.9804：98.04% 的測試情境中，模型推薦的第一名就是正確答案。換言之，僅約 1.96% 的案例第一名猜錯，用戶幾乎不需要看到第二個選項。


Recall@3 = 1.0000：只要看到前三名推薦，100% 能找到正確答案。這意味著模型保證正確答案不會落在第 4 名以後，對用戶體驗而言是最關鍵的保障指標。


Recall@5 = 1.0000：與 Recall@3 相同，說明所有正確答案均集中在前 3 名內，第 4、5 名對覆蓋率無額外貢獻。


MRR@1 = 0.9804：K=1 時 MRR 等於 Recall@1，因為只有一個候選位置。


MRR@3 = MRR@5 = 0.9896：正確答案平均排在 1 / 0.9896 ≈ 第 1.01 名，幾乎全部排在第 1 名，極少數排在第 2 名（1/2 = 0.5 拉低平均），無任何案例排在第 3 名以後（否則 MRR 會更低）。MRR@3 = MRR@5 代表第 4、5 名完全無正確答案，與 Recall@3 = 1.0 一致。


NDCG@1 = 0.9804：K=1 時 NDCG 等於 Recall@1，因為只有一個位置可放正確答案。


NDCG@3 = 0.9782：前三名的排序品質極高，略低於 Recall@3（1.0）是正常現象：NDCG 對未排在第 1 名的情況扣分（排第 2 名的增益為 log₂(3) ≈ 0.63），而 Recall 只看有無出現，不看排名。


NDCG@5 = 0.9767：略低於 NDCG@3，是因為理想分數（IDCG）的分母隨 K 增大，而實際能貢獻的正樣本只有一個，導致比值略降，屬正常的數學性質而非模型退步。

# 四、結論與未來方向

## 4.1 結論

本系統以 LightGBM LambdaRank 結合六類 count-based 特徵，在行程數 ≥ 20 筆的用戶群上達到 Recall@3 = 100%、Recall@1 = 98.04%、NDCG@1 = 98.04% 的表現，充分驗證個人化歷史行為特徵（user_end_freq）與上車地域特徵（start_end_freq）是下車地址預測的核心驅動力。整體訓練流程耗時約 3 分鐘（含資料處理），可快速迭代。

## 4.2 未來可改進方向

- 冷啟動處理：目前對行程數 < 20 筆的用戶使用全局熱門地址 fallback，可進一步引入協同過濾（找相似用戶的下車偏好）改善。
- 時序特徵：加入最近一次下車地址（recency）、距上次使用天數等時序信號，捕捉用戶行為漂移。
- 更多候選來源：目前候選集限於 suggestion 表中用戶曾去過的地址；對新地址可透過地理鄰近搜尋擴充候選集。
- 全量用戶訓練：本次因資源限制僅訓練 ≥ 20 筆用戶，未來可搭配更多負樣本策略對稀疏用戶也進行訓練。
