# 下車地址推薦系統(evaluate的方法有問題，還在修改，目前的結果跟baseline的SuggestionWeightedFusion應該差不多)
## Drop-off Address Recommendation System
### 模型訓練與評估報告 | AI 課程期末專案 × LineGO | 2026 年 6 月

---

## 一、問題描述

### 1.1 題目背景

本題由 LineGO 提出，核心目標為：在用戶輸入上車地址後，系統能即時推薦最有可能的下車地址排序清單，協助用戶快速完成叫車行為。題目要求推薦結果需考量不同時段、平日／假日差異，以及用戶個人屬性，以在不同叫車情境下提供最貼近用戶需求的建議。

傳統叫車流程中，用戶每次都需手動輸入目的地，耗時且容易重複輸入相同地點。若系統能根據歷史行為與當前情境主動預測目的地，可大幅降低叫車摩擦，提升使用體驗。

### 1.2 資料說明

本題提供兩張資料表，時間範圍均為 2026 年 1 月至 5 月：

**表 1｜address_v2_training_data（行程日誌）**

| 欄位名稱 | 資料型態 | 欄位說明 | 備註 |
|---|---|---|---|
| uid_hash | STRING | 乘客 ID 經 SHA256 雜湊後的匿名識別碼 | 64 字元 hex |
| start_latlng | STRING | 上車經緯度（精度至小數點第 2 位，約 1.1 km） | 區域級精度 |
| end_latlng | STRING | 下車經緯度（精度至小數點第 3 位，約 110 m） | 地址級精度 |
| created_at | TIMESTAMP | 叫車時間點（UTC） | |
| hour_type | STRING | 時段分類：凌晨、午夜、早尖峰、早離峰、午離峰、小晚尖、晚尖峰 | 共 7 類 |
| is_holiday | STRING | 是否為假日（"0" 平日 / "1" 假日） | |
| dayofweek | STRING | 星期幾（"1"~"7"） | |

資料規模：**1,000,000 筆**行程、325,717 位用戶，無缺失值，檔案大小約 305 MB。

**表 2｜address_v2_suggestion（地址對照表）**

| 欄位名稱 | 資料型態 | 欄位說明 | 備註 |
|---|---|---|---|
| uid_hash | STRING | 同上，乘客匿名識別碼 | 與訓練資料可 JOIN |
| end_latlng | STRING | 下車點經緯度（精度至小數點第 3 位） | JOIN key |
| end_address | STRING | 下車地址名稱（中文） | 推薦顯示用 |
| end_latlng_pin | STRING | 下車點精確經緯度（完整 pin 點） | 地圖定位用 |
| updated_date | DATE | 資料更新日期 | |

資料規模：**2,493,639 筆**、659,806 位用戶，無缺失值，檔案大小約 254 MB。此表作為推薦候選集來源，也提供經緯度對應真實地址名稱的查找功能。

### 1.3 目標輸出

給定用戶 ID、當前上車位置、時段、假日狀態及星期，系統輸出該用戶最有可能的 Top-K 下車地址排序清單。評估重點在於：正確答案是否排在前幾名、排名是否越前越好。

## 二、模型架構

### 2.1 整體設計思路

本系統採用兩階段推薦架構（Two-Stage Retrieval + Ranking），這是業界主流的推薦系統設計模式：

- **Stage 1｜候選集生成（Candidate Generation）**：從 `address_v2_suggestion` 表中撈出該用戶曾去過的所有下車地址，作為本次推薦的候選集。範圍窄、精準，避免從全量地址中盲目搜尋。
- **Stage 2｜排序（Ranking）**：對候選集中每個地址計算特徵，交由 LightGBM LambdaRank 模型打分排序，輸出 Top-K 推薦結果。

設計上刻意不做複雜的神經網路，原因是本題的最強信號（用戶歷史下車頻率）是高度稀疏的 count-based 特徵，樹模型在此類特徵上通常比深度學習更有效率，且訓練速度快、可解釋性高。

### 2.2 特徵工程

共設計 12 個特徵，分為原始頻率（6 個）與 log1p 轉換版（6 個）兩組。log1p 轉換用於壓縮頻率的長尾分佈，讓模型同時能捕捉絕對值與相對大小兩種訊號：

| 特徵名稱 | 類型 | 意義 |
|---|---|---|
| user_end_freq | 個人化 | 用戶歷史去過該下車地址幾次 |
| global_end_freq | 全局熱門度 | 全體用戶去過該下車地址的總次數（冷啟動 fallback） |
| hour_end_freq | 時段情境 | 相同時段（如早尖峰）去該地址的歷史頻率 |
| holiday_end_freq | 假日情境 | 相同假日/平日狀態下去該地址的歷史頻率 |
| dow_end_freq | 星期情境 | 相同星期幾去該地址的歷史頻率 |
| start_end_freq | 上車情境 | 從相同上車區域出發前往該地址的歷史頻率 |
| log_* × 6 | 對數轉換 | 上述六個特徵各自取 log1p，捕捉相對大小訊號 |

### 2.3 資料切分策略

為避免 data leakage，採用**時序切分**而非隨機切分。全量行程依 `created_at` 排序後，按筆數比例切成三個不重疊的時間段：

| Split | 比例 | 時間範圍 | 用途 |
|---|---|---|---|
| Train | 75% | 2026/01/01 ~ 2026/04/14 | 模型訓練 |
| Val | 10% | 2026/04/14 ~ 2026/04/27 | Early stopping 監控 |
| Test | 15% | 2026/04/27 ~ 2026/05/17 | 最終評估（訓練期間完全不碰） |

此外，頻率查找表（lookups）**只用 train 行程計算**，避免 val/test 期間的行程次數洩漏進特徵，確保評估結果反映真實部署條件。

### 2.4 訓練資料建立

對每一筆行程記錄，以「用戶 × 叫車情境」為一個 query，建立以下樣本：

- **正樣本（label = 1）**：該筆行程的真實下車地址
- **負樣本（label = 0）**：從同用戶候選集中隨機抽取 4 個非真實答案的地址（NEG_RATIO = 4）

### 2.5 模型：LightGBM LambdaRank

本系統採用 LightGBM 的 LambdaRank 目標函數，這是一種 Listwise Learning to Rank 方法：

- 與普通二分類不同，LambdaRank 以整個候選列表為單位進行優化，直接最大化 NDCG 排序指標
- 每個用戶的候選地址集合對應一個 group，模型學習「在同一個 query 裡，哪個候選地址應該排在前面」
- 使用 **Early Stopping（patience = 30）**，以 val NDCG 為監控指標，防止過擬合
- 主要超參數：學習率 0.05、葉節點數 63、最大迭代 500 輪，使用 GPU（NVIDIA T4）加速訓練

## 三、訓練結果

### 3.1 Step 1｜讀取資料與時序切分

| 項目 | 數值 |
|---|---|
| 執行時間 | 32 秒（3 步驟，平均 18.03 秒/步） |
| 有效用戶數 | 5,629 位（原始 325,717 位，過濾條件：行程數 ≥ 20） |
| 總有效行程數 | 174,794 筆 |

**時序切分結果：**

| Split | 筆數 | 用戶數 | 時間範圍 |
|---|---|---|---|
| train | 131,095 | 5,629 | 2026/01/01 ~ 2026/04/14 |
| val | 17,479 | 5,028 | 2026/04/14 ~ 2026/04/27 |
| test | 26,220 | 5,295 | 2026/04/27 ~ 2026/05/17 |

原始資料共有 325,717 位用戶，但大多數用戶歷史行程稀疏（中位數僅 1 筆），設定 `MIN_TRIPS = 20` 後，保留 5,629 位歷史豐富的用戶。val 的用戶數（5,028）略少於 train（5,629），代表少數用戶在 val 時段沒有行程，屬正常現象。test 用戶數（5,295）高於 val，顯示近期活躍用戶比例較高。

| 查找表 | 鍵值數量 | 說明 |
|---|---|---|
| user_end | 49,642 | 用戶 × 下車地址的唯一組合（僅計算 train 期間） |
| global_end | 16,252 | train 期間出現過的唯一下車地址數 |
| hour_end | 37,851 | 時段 × 下車地址的唯一組合 |

與舊版（全量計算）相比，各 lookup 的 key 數均下降，例如 `user_end` 從 60,866 降至 49,642，反映 val/test 行程不再參與統計。六張表共耗時不到 1 秒（17.30 table/s）。

### 3.3 Step 3｜建立訓練樣本

| Split | 樣本數 | pos_rate |
|---|---|---|

三個 split 的 pos_rate 均為 0.202，符合 `NEG_RATIO = 4` 的設定（1/5 = 0.2），且三者一致，代表切分品質穩定。

### 3.4 Step 4｜模型訓練

| 項目 | 數值 |
|---|---|
| 訓練裝置 | GPU（NVIDIA T4）|
| 最大迭代輪數 | 500 rounds |
| Early stopping patience | 30 rounds |
| **實際停止輪數** | **第 25 輪** |
| 訓練時間 | 約 20 秒（4.40 round/s） |
| 停止時 val NDCG@1 | 0.8013 |

模型在第 25 輪時 val NDCG@1 達到最佳值後，連續 30 輪未改善，於第 55 輪觸發 early stopping（25 + 30 = 55）。相較於舊版不設 early stopping 跑滿 300 輪，實際有效訓練輪數大幅減少，代表模型在少量輪次內就已充分學習，過多迭代反而有過擬合風險。

| 5 | global_end_freq | 13,021 | 全局熱門度 |
| 6 | log_hour_end_freq | 8,215 | 時段頻率 log 版 |
| 7 | dow_end_freq | 7,603 | 星期幾條件頻率 |
| 8 | log_global_end_freq | 5,940 | 全局熱門度 log 版 |
| 9 | log_dow_end_freq | 5,422 | 星期幾頻率 log 版 |
| 10 | hour_end_freq | 2,894 | 時段條件頻率 |
| 11 | log_holiday_end_freq | 826 | 假日頻率 log 版 |

與舊版（隨機切分）最顯著的差異在於：**`start_end_freq` 的 Gain 值從第二名（105,245）躍升至第一名（231,921），且差距大幅拉開**；而 `log_user_end_freq` 的 Gain 從 134,609 降至 49,659。這反映在時序切分下，用戶個人歷史對「未來」行程的預測力不如地域關聯強——當模型只能看過去的行程去預測未來，起點（上車區域）提供的情境信號比個人歷史頻次更穩定。

### 3.5 Step 5｜模型評估

**評估指標說明：**

| 指標 | 定義 |
|---|---|
| Recall@K | 正確答案是否出現在前 K 名（Hit = 1，否則 = 0） |
| MRR@K | Mean Reciprocal Rank，正確答案排名倒數的平均值（第 1 名 = 1.0，第 2 名 = 0.5） |
| NDCG@K | Normalized DCG，對排名位置加權後正規化的綜合品質分數 |

**評估結果：**

| K | Recall@K | MRR@K | NDCG@K |
|---|---|---|---|
| 1 | 0.8191 | 0.8191 | 0.8191 |
| 3 | 0.9511 | 0.8788 | 0.7541 |
| 5 | 0.9787 | 0.8851 | 0.7284 |

**與舊版（隨機切分）對比：**

| 指標 | 舊版（隨機切分） | 新版（時序切分） | 差距 |
|---|---|---|---|
| Recall@1 | 0.9804 | 0.8191 | -0.1613 |
| Recall@3 | 1.0000 | 0.9511 | -0.0489 |
| Recall@5 | 1.0000 | 0.9787 | -0.0213 |
| MRR@3 | 0.9896 | 0.8788 | -0.1108 |
| NDCG@3 | 0.9782 | 0.7541 | -0.2241 |

指標全面下降，這是**預期結果，代表評估更真實**。舊版用隨機切分，允許模型用「未來行程」預測「過去行程」，分數虛高；時序切分後，模型必須用歷史行為預測真正未來的目的地，難度更高，評估結果更接近實際上線表現。

**各指標逐項解讀：**

**Recall@1 = 0.8191**：約 82% 的情境下，第一名推薦就是正確答案，約 18% 需要用戶往下看。

**Recall@3 = 0.9511**：前三名能覆蓋約 95% 的正確答案，對用戶來說只需快速掃視三個選項即可完成叫車。

**Recall@5 = 0.9787**：前五名覆蓋率接近 98%，僅約 2% 的情境無法在前五名找到正確答案。

**MRR@3 = 0.8788**：正確答案平均排在 1/0.8788 ≈ 第 1.14 名，大多數情況排在第一，少數排在第二或第三。

**MRR@5 = 0.8851**：MRR@5 略高於 MRR@3（0.8851 vs 0.8788），代表有部分正確答案落在第 4 或第 5 名，但加入這些名次計算後整體平均稍微提升。

**NDCG@3 = 0.7541**：前三名的排序品質達到理想分數的 75.4%，低於 Recall@3（95.11%）是因為 NDCG 會對排名位置扣分——正確答案排第 2 名或第 3 名都會降低分數，而 Recall 只看「有沒有出現」。

**NDCG@5 = 0.7284**：略低於 NDCG@3，是 K 增大時 IDCG 分母增加的數學性質，並非模型退步。

## 四、結論與未來方向

### 4.1 結論

採用時序切分後，評估結果更真實地反映模型上線後的表現：Recall@1 = 81.91%、Recall@3 = 95.11%、NDCG@1 = 81.91%。雖然指標數字低於隨機切分版本，但具備更高的可信度。特徵重要性分析也揭示，在正確的評估設定下，**上車區域（start_end_freq）是最強的預測信號**，而非個人歷史頻率，這對未來特徵工程方向有重要的指導意義。

### 4.2 未來可改進方向

- **冷啟動處理**：目前對行程數 < 20 筆的用戶使用全局熱門地址 fallback，可引入協同過濾改善
- **時序特徵**：加入最近一次下車地址（recency）、距上次使用天數等信號，捕捉行為漂移
- **更多候選來源**：對新地址可透過地理鄰近搜尋擴充候選集，解決候選集覆蓋不足的問題
- **全量用戶訓練**：目前僅訓練行程數 ≥ 20 筆的用戶，可搭配稀疏用戶策略擴大訓練範圍
