# 下車地址推薦系統
## Drop-off Address Recommendation System
### 模型訓練與評估報告 | AI 課程期末專案 × LineGO | 2026 年 6 月

---

## 一、問題描述

### 1.1 題目背景

本題由 LineGO 提出，核心目標為：在用戶輸入上車地址後，系統能即時推薦最有可能的下車地址排序清單，協助用戶快速完成叫車行為。題目要求推薦結果需考量不同時段、平日／假日差異，以及用戶個人屬性，以在不同叫車情境下提供最貼近用戶需求的建議。

傳統叫車流程中，用戶每次都需手動輸入目的地，耗時且容易重複輸入相同地點。若系統能根據歷史行為與當前情境主動預測目的地，可大幅降低叫車摩擦，提升使用體驗。

### 1.2 資料說明

本題提供兩張資料表，時間範圍均為 2026 年 1 月至 5 月：

**表 1｜address_v2_training_data（行程日誌）**

| 欄位名稱 | 資料型態 | 欄位說明 | 備註 |
|---|---|---|---|
| uid_hash | STRING | 乘客 ID 經 SHA256 雜湊後的匿名識別碼 | 64 字元 hex |
| start_latlng | STRING | 上車經緯度（精度至小數點第 2 位，約 1.1 km） | 區域級精度 |
| end_latlng | STRING | 下車經緯度（精度至小數點第 3 位，約 110 m） | 地址級精度 |
| created_at | TIMESTAMP | 叫車時間點（UTC） | |
| hour_type | STRING | 時段分類：凌晨、午夜、早尖峰、早離峰、午離峰、小晚尖、晚尖峰 | 共 7 類 |
| is_holiday | STRING | 是否為假日（"0" 平日 / "1" 假日） | |
| dayofweek | STRING | 星期幾（"1"~"7"） | |

資料規模：**1,000,000 筆**行程、325,717 位用戶，無缺失值，檔案大小約 305 MB。

**表 2｜address_v2_suggestion（地址對照表）**

| 欄位名稱 | 資料型態 | 欄位說明 | 備註 |
|---|---|---|---|
| uid_hash | STRING | 同上，乘客匿名識別碼 | 與訓練資料可 JOIN |
| end_latlng | STRING | 下車點經緯度（精度至小數點第 3 位） | JOIN key |
| end_address | STRING | 下車地址名稱（中文） | 推薦顯示用 |
| end_latlng_pin | STRING | 下車點精確經緯度（完整 pin 點） | 地圖定位用 |
| updated_date | DATE | 資料更新日期 | |

資料規模：**2,493,639 筆**、659,806 位用戶，無缺失值，檔案大小約 254 MB。此表同時作為推薦候選集來源，以及經緯度對應真實地址名稱的查找表。

### 1.3 目標輸出

給定用戶 ID、當前上車位置、時段、假日狀態及星期，系統輸出該用戶最有可能的 Top-K 下車地址排序清單（以 `end_latlng` 表示）。評估重點在於正確答案是否排在前幾名、排名是否越前越好。

## 二、模型架構

### 2.1 整體設計思路

本系統採用兩階段推薦架構（Two-Stage Retrieval + Ranking），這是業界主流的推薦系統設計模式：

- **Stage 1｜候選集生成（Candidate Generation）**：從 `address_v2_suggestion` 表中撈出該用戶曾去過的所有下車地址，作為本次推薦的候選集。若用戶無歷史記錄（新用戶），fallback 到全局最熱門地址。
- **Stage 2｜排序（Ranking）**：對候選集中每個地址計算特徵，交由 LightGBM LambdaRank 模型打分排序，輸出 Top-K 推薦結果。

設計上採用樹模型而非神經網路，原因是本題的核心信號（用戶歷史下車頻率）是高度稀疏的 count-based 特徵，樹模型在此類特徵上通常比深度學習更有效率，且訓練速度快、可解釋性高。

### 2.2 特徵工程

共設計 12 個特徵，分為原始頻率（6 個）與 log1p 轉換版（6 個）兩組。log1p 轉換用於壓縮頻率的長尾分佈，讓模型同時能捕捉絕對值與相對大小兩種訊號。**所有特徵均只從 train 行程計算**，不使用 val/test 期間的資料，避免 data leakage。

| 特徵名稱 | 類型 | 意義 |
|---|---|---|
| user_end_freq | 個人化 | 用戶歷史去過該下車地址幾次 |
| global_end_freq | 全局熱門度 | 全體用戶去過該下車地址的總次數（冷啟動信號） |
| hour_end_freq | 時段情境 | 相同時段（如早尖峰）去該地址的歷史頻率 |
| holiday_end_freq | 假日情境 | 相同假日/平日狀態下去該地址的歷史頻率 |
| dow_end_freq | 星期情境 | 相同星期幾去該地址的歷史頻率 |
| start_end_freq | 上車情境 | 從相同上車區域出發前往該地址的歷史頻率 |
| log_* × 6 | 對數轉換 | 上述六個特徵各自取 log1p，捕捉相對大小訊號 |

### 2.3 資料切分策略

為避免 data leakage，採用**時序切分**而非隨機切分。全量 1,000,000 筆行程依 `created_at` 排序後，按筆數比例切成三個不重疊的時間段，確保 train 永遠比 val/test 更早：

| Split | 比例 | 筆數 | 用戶數 | 時間範圍 | 用途 |
|---|---|---|---|---|---|
| Train | 75% | 750,000 | 273,683 | 2026/01/01 ~ 2026/04/14 | 模型訓練、特徵計算 |
| Val | 10% | 100,000 | 65,461 | 2026/04/14 ~ 2026/04/28 | Early stopping 監控 |
| Test | 15% | 150,000 | 89,435 | 2026/04/28 ~ 2026/05/17 | 最終評估（訓練期間完全不碰） |

### 2.4 訓練樣本建立

對每一筆行程記錄，以「用戶 × 叫車情境」為一個 query，從 suggestion 表的候選集中配對正負樣本：

- **正樣本（label = 1）**：該筆行程的真實下車地址
- **負樣本（label = 0）**：從同用戶候選集中隨機抽取最多 4 個地址（NEG_RATIO = 4）

750,000 筆行程共產生約 320 萬訓練樣本（理論上限 750k × 5 = 3,750k，實際因部分用戶候選集不足而略少）。

### 2.5 模型：LightGBM LambdaRank

採用 LightGBM 的 LambdaRank 目標函數，這是一種 Listwise Learning to Rank 方法：

- 以整個候選列表為單位優化，直接最大化 NDCG 排序指標，而非逐筆做二分類
- 每個用戶的候選地址集合對應一個 group，模型學習「在同一個 query 裡，哪個候選地址應該排在前面」
- 使用 **Early Stopping（patience = 30）**，以 val NDCG 為監控指標，防止過擬合
- 主要超參數：學習率 0.05、葉節點數 63、最大迭代 500 輪，使用 GPU（NVIDIA T4）加速

### 2.6 評估方式

評估採用與組員 baseline 相同的介面（`evaluate.py`），以**每一筆行程為一個獨立 query**，對 val 和 test 各做一次完整評估：

| 指標 | 定義 |
|---|---|
| Hit@K | 正確答案是否出現在前 K 名（= Recall@K，因每筆 query 只有 1 個正解） |
| MRR | Mean Reciprocal Rank，正確答案排名倒數的平均值 |
| NDCG@K | Normalized DCG，對排名位置加權後正規化的綜合品質分數 |

### 3.4 模型訓練

（此節數據待本次訓練完成後補充，以下為架構說明）

使用全量 3,227,255 筆訓練樣本，以 val 的 428,468 筆作為 early stopping 監控依據，GPU 訓練，最大迭代 500 輪，patience = 30。

### 3.5 模型評估

**Val split 結果（100,000 筆）：**

| K | Hit@K | MRR | NDCG@K |
|---|---|---|---|
| 1 | 0.3617 | 0.3617 | 0.3617 |
| 3 | 0.5979 | 0.4642 | 0.4984 |
| 5 | 0.7228 | 0.4926 | 0.5498 |

**Test split 結果（150,000 筆）：**

| K | Hit@K | MRR | NDCG@K |
|---|---|---|---|
| 1 | 0.3495 | 0.3495 | 0.3495 |
| 3 | 0.5917 | 0.4545 | 0.4896 |
| 5 | 0.7185 | 0.4834 | 0.5418 |

**各指標解讀：**

**Hit@1（val=0.3617, test=0.3495）**：約 35% 的情境下，第一名推薦就是正確答案。val 略高於 test，顯示時間越近的資料（test 為最新 15%）越難預測，符合真實情況。

**Hit@3（val=0.5979, test=0.5917）**：前三名能覆蓋約 60% 的正確答案，相較 Hit@1 提升約 24pp，代表有一大部分正確答案落在第 2、3 名，值得在 UI 上顯示至少 3 個選項。

**Hit@5（val=0.7228, test=0.7185）**：前五名覆蓋率達 72%，對大多數用戶而言只需在五個選項中點選即可完成叫車。Val 與 test 差距僅 0.4pp，說明模型在不同時間段的穩定性良好。

**MRR（val=0.4926, test=0.4834）**：正確答案平均排在約第 2 名（1/0.49 ≈ 2.04），代表模型排序合理但仍有進步空間，理想情況應達到 MRR > 0.6（平均第 1~2 名之間）。

**NDCG@5（val=0.5498, test=0.5418）**：前五名的排序品質達到理想分數的 55%，介於 Hit@5 和 MRR 之間，符合指標的數學性質（每筆只有 1 個正解時 NDCG@K 落在兩者之間）。

### 3.6 與組員 Baseline 對比

以下對比使用相同的評估框架（`evaluate.py`）、相同的 val split（100,000 筆）：

| 模型 | Hit@1 | Hit@3 | Hit@5 | MRR | NDCG@5 |
|---|---|---|---|---|---|
| GlobalPopularity | 0.0094 | 0.0197 | 0.0264 | 0.0153 | 0.0180 |
| UserHistory | 0.2165 | 0.3258 | 0.3513 | 0.2721 | 0.2921 |
| UserContextHistory | 0.2496 | 0.3315 | 0.3541 | 0.2915 | 0.3073 |
| HybridContextCascade | 0.2625 | 0.3622 | 0.3938 | 0.3142 | 0.3342 |
| HybridContextPlus | 0.2723 | 0.3634 | 0.3941 | 0.3198 | 0.3385 |
| **本模型（LightGBM）** | **0.3617** | **0.5979** | **0.7228** | **0.4926** | **0.5498** |

本模型在所有 train-only baseline 中表現最佳：Hit@1 超過 HybridContextPlus 約 8.9pp，Hit@5 超過 39.4pp，NDCG@5 超過 21.1pp。與 overall SOTA（SuggestionWeightedFusion）相比，Hit@5 差距縮小至 2.3pp，NDCG@5 差距為 3.7pp。

## 四、結論與未來方向

### 4.1 結論

本系統以 LightGBM LambdaRank 結合六類 count-based 特徵，在全量用戶（325,717 位）、正確時序切分的評估設定下，test Hit@5 = 71.85%、NDCG@5 = 54.18%，超越所有 train-only 規則式 baseline，並在 Hit@5 上接近使用 suggestion 表加權融合的 SuggestionWeightedFusion（差距 2.3pp）。

本次實作也修正了先前評估的 data leakage 問題：原先隨機切分 + MIN_TRIPS=20 的設計造成指標虛高（Hit@1 高達 0.98），改為時序切分、全量用戶、row-level 評估後，指標回到與 baseline 同等量級的真實水準，具有更高的可信度。

### 4.2 未來可改進方向

- **加入 suggestion 表特徵**：將該地址在 suggestion 表中的出現頻率加入特徵，這是 SuggestionWeightedFusion 領先的主要來源，預期能進一步縮小差距
- **時間衰減**：對近期行程給予更高權重，user_end_freq 目前是全部歷史等權重加總，加入時間衰減可更好反映近期偏好
- **冷啟動優化**：目前新用戶 fallback 全局熱門，可引入 start 共現（`start_end_freq`）或協同過濾改善
- **候選集擴充**：對 suggestion 表中無記錄的用戶，可透過地理鄰近搜尋擴充候選集
